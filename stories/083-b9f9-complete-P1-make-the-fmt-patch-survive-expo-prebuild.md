# Make the fmt patch survive expo prebuild

## Problem Statement

React Native 0.79.6 vendors fmt 11.0.2, whose FMT_STRING consteval path the clang in Xcode 26 rejects. Without a patch, no native iOS build of this app compiles at all - the failure is in React Native's own pod and has nothing to do with any feature. A working patch exists and was proven to build and install the app on an iOS 26.5 simulator, but it lives in ios/Podfile, which is gitignored and regenerated by every expo prebuild. So it silently vanishes and the next person hits an unexplained compiler error in a vendored dependency. It cannot be fixed from build settings: base.h sets FMT_USE_CONSTEVAL through an unguarded if/elif chain with no ifndef, so an external define is overridden by the header.

## Acceptance Criteria

- [x] The patch lives in the repository as an Expo config plugin rather than in the generated ios/Podfile
- [x] Running expo prebuild from clean, then pod install, applies it automatically with no manual step
- [x] A native iOS build compiles React Native's fmt pod and links successfully
- [x] The plugin is a no-op when fmt already carries the upstream fix, so it does not have to be removed by hand later
- [x] The plugin explains why it exists and names the upstream fix (fmt 11.1) that retires it
- [x] CocoaPods installs pod sources read-only, so the plugin must restore write permission before patching

## Work Log

### 2026-09-14T01:11:33.793Z - Moved the fmt consteval patch out of the gitignored ios/Podfile into client/plugins/with-fmt-consteval-fix.js, registered in client/app.json. The file is dual-purpose: as an Expo config plugin it uses withPodfile to re-inject a post_install hook on every prebuild; as a CLI it is what that hook calls, so the patching logic lives in one testable place instead of in generated Ruby.

Detection is shape-based, not version-based. fmt 11.1's FMT_USE_CONSTEVAL chain is byte-identical to 11.0.2's, so keying on the chain would wrongly patch a fixed fmt. The real upstream fix is that basic_format_string was replaced by fstring whose compile-string overload is no longer FMT_CONSTEVAL, so the plugin looks for a FMT_CONSTEVAL basic_format_string constructor and no-ops without it. Verified against the real fmt 11.1.0 header: not-needed, file and permissions untouched.

Contrary to the task brief, Xcode 26.6 and CocoaPods 1.17.0 were available, so criteria 2 and 3 were proven rather than deferred. expo prebuild --clean wiped ios/ (the old manual fmt_base Ruby patch went to zero occurrences) and the plugin re-injected the hook automatically; pod install then printed the patched line for Pods/fmt/include/fmt/base.h. A full xcodebuild for the iOS Simulator exited 0 with zero error lines, producing libfmt.a (1.9 MB) and a linked indriclient.app.

Decisive toolchain proof: compiling a FMT_STRING translation unit with the real Xcode 26 clang fails on pristine fmt 11.0.2 with 'call to consteval function fmt::basic_format_string<...> is not a constant expression' and compiles OK against the patched header.

11 new tests in client/plugins/with-fmt-consteval-fix.node-test.ts (413/413 suite green) cover the patch rewriting exactly one line, the 11.1 no-op, idempotence of both the header and Podfile patches, a loud raise when fmt is broken but unrecognisable or the Podfile has no post_install block, and a real 0444 fixture proving the chmod. Console output is captured and asserted rather than left as test noise. Also verified the injected Ruby parses (ruby -c), executes end-to-end against a fake installer, and raises when the script is missing; and that expo config --type prebuild resolves the app.json entry, with a negative control confirming it exits 1 when the plugin file is absent. No new dependencies; pnpm install --frozen-lockfile still in sync.
