# Adversarial verification: client/layout + transport findings

Worktree `.worktrees/codebase-review` (read-only; `git status` clean after the run). Client code in the worktree matches 3eab208 (`git diff --stat 3eab208 -- client` is empty). The client probes ran against a scratch copy of `client/` with node_modules symlinked from the main checkout (node v25.5.0, real fengari / fengari-interop). The Go probe ran through `go test -overlay` in `internal/handlers/actions/layout`. Probes and the case file are in `scratchpad/verify-client/`.

| CL-1 | **CONFIRMED P1** (exploit syntax in the report is wrong) | `host-api.ts:292-295` pushes a live JS object through `fengariInterop.push`. `indri.state().constructor.constructor` reaches `function Function()`. The report's `F("src")()` does NOT run: it returns `function anonymous(){}` / nil, because fengari-interop passes the first Lua argument as JS `this`. `F(nil, "globalThis.PWNED3='yes'; return 7")(nil)` returns 7 and sets the global. This also works in the real BoardView order. The scene script runs first, while `currentGame` is undefined (`indri.state()` is nil at the top level), but `indri.on("stateChanged", function() ... F(nil, src)(nil) end)` executed arbitrary JS on the next `onStateChange`. Who can author it: only the `layout` action (`handler.go:31` `RequireHost`), plus the operator's script file. Any registered user who creates a game becomes host (`operations.go:151` `host := !gameHasHost(g)`). So this is any user → every player who joins their game code: arbitrary JS in the victim's app context (tokens, storage, network). P1 stands. | — |
| CL-2 | **CONFIRMED, SEVERITY-ADJUST → P2** | Reproduced. `error({})`, `error(nil)`, and even `error(setmetatable({}, {__tostring=...}))` all throw `TypeError: to_jsstring expects a Uint8Array` out of both `runScript` (`host-api.ts:231`) and `runChunk` (`runtime.ts:83`). `error("str")` / `error(42)` return `{ok:false}` correctly. `indri.log` of a cyclic table also throws (`luaTableToJs` has no cycle guard). The `indri.on` handler path is guarded (`host-api.ts:325-326`) and did not throw. The throw lands in the `board-view.tsx:99` useEffect, and there is no ErrorBoundary anywhere in `client/app`, `components` or `providers`. Downgraded because only the host can trigger it, and a malicious host already gets strictly more through CL-1. What's left on its own is an honest-mistake crash. | — |
| CL-3 | **CONFIRMED divergence, SEVERITY-ADJUST → P3**, broader than reported | Ran through both validators. Go `ValidateLayout` → nil, TS `parseLayout` → no layout (blank board) for: absolute `left:"abc"` (A), `kind:"foo"` (B), absolute with no fields (C). Two more cases the report missed behave the same way: a widget with no `placement` (H) and an unknown widget `type` (I). Go deliberately never checks widget type/config/style (`validate.go:26-28`, op.go stores `widget`/`config`/`style` verbatim), so fixing placements alone does not close the "host blanks the board" path. **A reverse divergence was also found:** absolute `z:1` is valid in TS (`placement.ts:23`), but Go rejects it (`validate.go:170-178` treats every numeric key as a "pixel number"), so an absolute widget with `z` can never be written. Severity is lower because only the host of that game can do this, to their own game. | — |
| CL-4 | **CONFIRMED, SEVERITY-ADJUST → P3** | Case E: two nested subgrid children at the same cell. Go rejects it (`scene "main/sg" widgets "a" and "b" overlap`), and TS accepts it with zero issues. Case G: a nested child at (10,10) inside a 20×20 subgrid. Go rejects it against the root 8×8 grid (`validate.go:118` passes the root `cols, rows`), which confirms the parenthetical bug. Case F: a child outside the subgrid's own 2×2 grid but inside the root. Both sides accept it. Impact is low: nested placements are not used for rendering at all (`subgrid/index.tsx` ignores `placement`), and the client editor has no nested-widget ops (`layout/edit/ops.ts` addresses scene-level `widgetId` only). | — |
| TR-1 | **CONFIRMED race, SEVERITY-ADJUST → P3** | pion v4.2.22 `datachannel.go:244` runs the OnOpen handler in `go openHandlerOnce.Do(...)`, and `:377` starts `go d.readLoop()` separately. Both are spawned from `handleOpen` after `sctptransport.go:358` has waited for the OnDataChannel handler (which registers OnOpen/OnMessage), so nothing orders them. `QueuedConn.Deliver` (`hub.go:171`) does not wait for Connected. The leak variant is real as well: `close()` → `Hub.Remove` → `Disconnected` (which sets `disconnected`, so a later `Connected` is a no-op). A late OnOpen still calls `Hub.Add` (`webrtc.go:292`), and nothing removes that entry again. Downgraded because the shipped client never sends on open: login/reconnect are user-driven, and no protocol-client adapter sends from `onopen` except graphqlws's `connection_init`. Both windows are microseconds. | Review A #7 |
| TR-2 | **CONFIRMED, SEVERITY-ADJUST → P3** | melody v1.3.0 `session.go:30-34`: a full buffer → `errorHandler(ErrMessageBufferFull)`, and `Write` returns nil (`:154-161`). The app Error handler only logs (`boot/handlers.go:34-36`). But for ws, `writeRaw` sets `WriteWait` (10s default) on every write (`session.go:42`), and a failed write ends `writePump` → `s.close()` (`:84-86,109`). A client that really stops reading is disconnected within about 10s. To drop frames while staying connected, ws needs more than 1024 frames queued inside one write-timeout window, which is unlikely for a party game. On sse/graphqlws the drop-and-stay-connected case exists only because of TR-3. | overlaps TR-3; Review B #10 |
| TR-3 | **CONFIRMED, SEVERITY-ADJUST → P3 (borderline P2)** | `SetWriteDeadline` appears exactly once in `internal/transport`: sse.go:72, which clears it. graphqlws never sets one. SSE: `emit` blocks in `io.WriteString` with no deadline. Kick only closes `done` (`hub.go:112-121`, teardown nil), and the shutdown path (`http.go:28-43`) just calls `Transport.Close` then `server.Shutdown` with a 10s ctx, so a stuck stream is never unblocked. graphqlws: `reply` (`:310-315`) blocks once 16 `ctrl` slots fill while the writer is stuck in `WriteJSON`. The read loop then never reaches `ReadMessage`, so the read deadline never fires, and `shutdown`/`closeWith` (whose `ws.Close()` would unblock the writer) is never called. Downgraded: sse/graphqlws are opt-in through `INDRI_TRANSPORTS` (ws is the default). An attacker already gets unbounded idle connections via TR-9, so the extra harm is mainly that kick and clean shutdown fail. A legitimate graphqlws client that vanishes still recovers through PongWait unless `ctrl` is full. | related TR-9, TR-17 |
| DP-1 (client part) | **CONFIRMED P2 (multi-instance only)** | `game-state-parser.ts:54-58` drops any delta with `t < cutoff`, and `:49-51` orders by `t`. Both are wall-clock values: `changes.go:81` `Timestamp: time.Now()` and the store's `UpdatedAt = time.Now()`, taken on whichever instance wrote. With a single instance the ordering holds (serialized writes, delta `t` is after its own `UpdatedAt`). Cross-instance clock skew under `INDRI_LOCK_BACKEND=redis` breaks both the ordering and the cutoff. | — |
